# Prototyping Apple App Design

## Overview

A design prototype exists to be **looked at**. Its output is screens someone can judge, not a program that compiles.

**Core principle:** `BUILD SUCCEEDED` is not evidence. A screen you have not seen rendered is a screen you have not designed.

The prototype is throwaway; the design is not. Everything the real app will replace — network, storage, auth — hides behind one protocol so production keeps the screens and swaps the implementation.

## When to Use

- "Prototype / mock up / design an app for iPhone, Mac, Watch…"
- Working out layout, hierarchy, and native feel before production code exists
- Producing a visual reference to hand to a real app that may use UIKit or AppKit

**Not for:** production features, real persistence or networking, or adding screens to an existing shipping app (match that app's conventions instead).

## Contract

Every prototype has these parts. This is the shape, not a suggestion:

| Part | Rule |
| --- | --- |
| Project | Generated by `scripts/new-prototype.ts`. Never hand-write a `.xcodeproj`. |
| Domain models | Plain `struct`s, no SwiftUI or storage types. Survive to production. |
| The seam | One protocol per capability. Views never name a concrete backend. |
| Mock | Implements the seam from fixtures. Deleted at production time. |
| Screens | Registered in `ScreenCatalog.swift`, or they are invisible to gallery and capture. |
| Phases | Every data-backed screen designs **loading, empty, loaded, failed**. |
| Previews | Data-backed screen: one `#Preview` per phase. Every screen: dark and an accessibility text size. |
| Fixtures | Realistic names, lengths, and dates. Lorem ipsum hides layout bugs. |
| Variants | When the ask is exploratory, 2–4 `Variant` cases that genuinely disagree. |
| Content | Nothing on screen that the design doesn't need. No filler rows, no invented stats. |

Every command in this skill is run from the project root, where its scripts sit under `.agents/skills/prototyping-apple-app-design/scripts/`.

## Workflow

1. **Ask before designing.** A new or vague brief gets one focused round of questions — platforms and which is primary, existing app or brand to match, the closest Apple app, the screens in scope, navigation model, how by-the-book versus distinctive, and how many variations on which dimension. Cover the question bank in [REFERENCE.md](REFERENCE.md) and ask about a dozen. Skip this only for small tweaks, follow-ups, or a brief that already answers it. Starting a design without context is how prototypes come back wrong.
2. **Ground the design in Apple's.** Read the relevant HIG page first. If an app in `bun .agents/skills/prototyping-apple-app-design/scripts/apple-ref.ts --list` solves a similar problem, capture it and study its structure; if none does, or the capture lands on onboarding, say so and rely on the HIG page. Either way, decide the layout _after_ this, not before.
3. **Generate the project.** `bun .agents/skills/prototyping-apple-app-design/scripts/new-prototype.ts "Display Name" <dir>`.
4. **Replace the `Note` domain** in `Shared/Backend` with the real subject: models, protocol, mock, fixtures.
5. **Build screens** in `Shared/Features`, registering each in `ScreenCatalog.swift`. System components first — `List`, `Form`, `ContentUnavailableView`, `.toolbar`. Exploratory ask? Add `Variant` cases and branch, rather than picking for the user.
6. **Capture and look.** `bun .agents/skills/prototyping-apple-app-design/scripts/shoot.ts --project <dir> --all`, then read the PNGs. Repeat per state, appearance, and variant. Fix what the screenshots show.
7. **Hand off.** Write `DESIGN-NOTES.md`: screen inventory, the tokens chosen, the options offered, and the exact seam a production implementation replaces.

## Quick Reference

```bash
SKILL=.agents/skills/prototyping-apple-app-design

bun $SKILL/scripts/new-prototype.ts "Reading Tracker" ~/Prototypes/reading
bun $SKILL/scripts/new-prototype.ts --watch "Habit Tracker" ~/Prototypes/habits
bun $SKILL/scripts/shoot.ts --project DIR --all                        # every screen
bun $SKILL/scripts/shoot.ts --project DIR --screen noteList --condition failing
bun $SKILL/scripts/shoot.ts --project DIR --screen noteList --appearance dark
bun $SKILL/scripts/shoot.ts --project DIR --screen noteList --text-size accessibility3
bun $SKILL/scripts/shoot.ts --project DIR --screen noteList --all-variants
bun $SKILL/scripts/shoot.ts --project DIR --platform macos --all       # real Mac window
bun $SKILL/scripts/apple-ref.ts --list                                 # Apple apps available
bun $SKILL/scripts/apple-ref.ts --app reminders --app settings         # design references
bun $SKILL/scripts/check-symbols.ts DIR                                # catch invented SF Symbols
bun $SKILL/scripts/contact-sheet.ts --project DIR --out /tmp/sheet.png    # compare a matrix at once
```

One target covers iPhone, iPad, Mac, and Vision Pro; `--watch` adds a watchOS target. tvOS is opt-in (see REFERENCE.md).

The user keeps Xcode open on the same folder; `#Preview` and edits stay live in both directions. Never delete a preview to "clean up".

## Rationalizations

| Excuse | Reality |
| --- | --- |
| "It builds, so the design is done." | The compiler cannot see a layout. Capture it. |
| "I screenshotted the main screen." | Every screen and every phase, or it is unreviewed. |
| "The store is basically the seam." | A concrete type in a view is a rewrite later. Protocol or nothing. |
| "I'll add empty and error states later." | They are the design. Later means never. |
| "Lorem ipsum is fine for now." | Fake text hides truncation, wrapping, and date formats. |
| "I know what Apple's app looks like." | Recollection produces generic look-alikes. Capture it. |
| "A quick unit test proves the flow." | Mock logic is throwaway. Tests here buy nothing. |
| "I'll hand-edit the pbxproj, it's small." | It is the single biggest time sink. Use the generator. |
| "The brief was clear enough to start." | Platform priority, existing brand, and scope are never in a one-line brief. Ask. |
| "I picked the strongest option to save a round trip." | An exploratory ask wants options rendered, not a decision made for them. |
| "A few extra rows make it feel real." | Filler content is a design smell. Every element earns its place. |

## Red Flags — Stop

- Reporting a prototype done without having viewed the screenshots
- A view that mentions `Mock…` by name
- A screen showing only content, with no loading/empty/failure treatment
- Invented hex colors and point sizes where system semantics belong
- Unit tests, persistence, auth, or networking in a design prototype
- Editing `project.pbxproj` by hand
- Designing before asking anything about platform, context, or scope
- One direction offered when the ask was "explore" or "show me options"
- Custom Liquid Glass on content-layer surfaces

## Common Mistakes

| Mistake | Correction |
| --- | --- |
| Serif/gradient "editorial" look on a native app | Use system fonts and semantic colors; earn deviations |
| Screen missing from the gallery | Register the case in `ScreenCatalog.swift` |
| Valueless launch flag (`-capture`) | Always `-key value`; a bare flag leaves macOS windowless |
| Fixed `sleep` before a screenshot | The harness has a readiness handshake; use `shoot.ts` |
| Reusing the user's booted simulator | `shoot.ts` provisions its own device |

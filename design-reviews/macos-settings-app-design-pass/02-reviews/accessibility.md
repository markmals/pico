# Accessibility and inclusion review

Reviewer: accessibility and inclusion. Brief version 1. Evidence: index of 2026-11-07.

Method note for every contrast number below: I opened the named PNG and sampled pixels with Pillow in a throwaway venv (no app launched). Captures are 1430 × 1698 px for a 715 × 849 pt window, i.e. exactly 2×, so glyph cores resolve to their true color. I report the darkest (light mode) / lightest (dark mode) pixel in a named crop against the modal background of that crop, and compute the WCAG relative-luminance ratio. Sampled values land exactly on macOS system label colors (38 ≈ `labelColor`, 124 ≈ `secondaryLabelColor`, 183 ≈ disabled control text at 247 background), which supports that these are the real colors and not antialiasing.

## Findings

### ACC-1 Row relationships exist only visually; several rows are read as loose fragments

- **Observation:** From the AX outlines (not speech — VoiceOver was not run). In `13-scratch-models-set-light.ax.txt` lines 50–63 the Available models list is a flat run of `AXStaticText`: `"gpt-oss-20b"`, `"lm-studio/openai/gpt-oss-20b"`, `"Default"`, `"Devstral Small"`, … The `"Default"` marker is a sibling between two models, so nothing but source order says which model it marks. Same shape in `04-tools-light.ax.txt` lines 43–83 (`"Read"` then `"Included"`, ×11 tools), `01-general-light.ax.txt` lines 71–81 (Versions: `"Pico app"`, `"Not connected"`, `"pico"`, `"Not connected"`, `"OMP"`, `"Not connected"`), and `05-sesh-light.ax.txt` lines 52–59, where `AXButton description="Register" disabled` sits between the `"Sesh custom agent"` row and the `"Connection status"` row with no stated owner. Separately, every `LabeledContent` trailing value is exposed twice as nested identical `AXStaticText` (`01-…ax.txt` 46–47, 52–53, 57–58, 65–66, 73–80; `13-…ax.txt` 56–57) while plain `Text` in the same forms is not (`02-…ax.txt` 52), so the duplication tracks `LabeledContent` specifically. Code: `app/Panes/ModelRows.swift:87-99`, `app/Panes/ToolPolicyRow.swift:9-21` and `app/Shared/SettingsValueRow.swift:15-25` add no accessibility grouping, whereas `app/Runtime/RuntimeCheckRow.swift:30-31` and `app/Panes/SettingsFileRow.swift:36-37` use `.accessibilityElement(children: .contain)` + label, and `app/Panes/AppIdentityRow.swift:13`, `app/Runtime/RuntimeActivityStatus.swift:12`, `app/Search/SearchResultsList.swift:40` use `.combine` — three different granularities for the same visual row idiom. Also in every outline the sidebar contains four unnamed rows (`01-…ax.txt` 5–7, 11–13, 20–22, 29–31: `AXCell > AXGroup/AXHostingView`, no description), matching the four groups in `app/Navigation/SettingsDestination.swift:14-19`.
- **Principle/source:** Apple HIG, _VoiceOver_ → Navigation: “**Specify how elements are grouped, ordered, or linked.** … Examine your app for places where relationships among elements are visual only. Then, describe these relationships to VoiceOver,” with the explicit image/caption grouping example. https://developer.apple.com/design/human-interface-guidelines/voiceover (accessed 2026-11-07; platform design guidance, primary source). Supporting: HIG _Accessibility_ → “An accessible interface is … Perceivable.” Same page set.
- **User impact:** Hits brief job 2 (choose the default model) and job 4 (understand the fixed tool policy). A VoiceOver user confirming which model is the default hears `"Default"` after the identifier of one model and before the name of the next; on Tools they traverse 11 tools × 3 stops with the verdict detached from the tool. Plausible, not demonstrated — I did not run VoiceOver; what is demonstrated is the tree shape.
- **Recommendation:** **[polish]** (this is “how a screen meets an accessibility commitment”). Adopt one row idiom: `.accessibilityElement(children: .combine)` on `ToolPolicyRow`, `SettingsValueRow` and each `AvailableModelRows` row, so each reads as `"Wait, Included"` / `"Pico app, Not connected"` / `"gpt-oss-20b, lm-studio/openai/gpt-oss-20b, Default"`. Give the `Register` button an `.accessibilityLabel` naming its row, or move it into that row’s `LabeledContent`. Tradeoff: `.combine` removes per-fragment navigation, so a long model identifier can no longer be reviewed word-by-word as its own element — acceptable here because the identifier is also selectable text; and `.combine` would need care on `SettingsFileRow`, which contains buttons and a disclosure (keep `.contain` there).
- **Severity / confidence:** high / high (tree shape directly observed; speech inferred).
- **Validation needed:** With VoiceOver on, VO-arrow through Models › Available models and Tools and record the actual utterances; check in Accessibility Inspector whether the nested duplicate `AXStaticText` is a separate stop or a non-visited wrapper. Confirm whether VoiceOver stops on the four unnamed sidebar group rows.

### ACC-2 The “unavailable / not set” state is drawn at 1.87:1 — the one state the brief says must stay visible

- **Observation:** I opened `02-models-light.png` and measured the Reasoning level popup value `"Unavailable"` (crop x 1150–1300, y 385–415): text #B7B7B7 on #F7F7F7, **1.87:1**, while the row label `"Model"` in the same row measures #262626 on #F7F7F7, **14.13:1**. Identical 1.87:1 for `"Not Set"` on the disabled Reasoning level row in `11-scratch-models-not-set-light.png` (where the enabled Model row’s `"Not Set"` measures 14.13:1 — the same two words, 7.5× apart in contrast, one row above the other) and for `"Unavailable"` in `14-scratch-models-saved-unavailable-light.png`. Dark mode is no better: the disabled `"Add Provider…"` title in `45-providers-dark.png` is #5C5C5C on #262626, **2.26:1** (light twin in `03-providers-light.png`: **1.86:1**). Code: `app/Shared/UnavailablePicker.swift:9-14` renders the reason as the single tag of a `.disabled(true)` `Picker`, so the reason text inherits the disabled control color; the AX side is correct (`02-…ax.txt:46` `AXPopUpButton description="Reasoning level" value="Unavailable" disabled`), the pixels are not.
- **Principle/source:** Apple HIG, _Accessibility_ → Vision: contrast table — text up to 17 pt, all weights, **minimum 4.5:1**; “If your app doesn’t provide this minimum contrast by default, ensure it at least provides a higher contrast color scheme when the system setting Increase Contrast is turned on”; “make sure to check the minimum contrast in both light and dark appearances.” https://developer.apple.com/design/human-interface-guidelines/accessibility (accessed 2026-11-07; platform design guidance, primary source). Maps to WCAG 2.2 SC 1.4.3; note WCAG exempts inactive controls, so the binding requirement here is the brief’s own rule that unconnected controls stay _visibly_ unconnected (`AGENTS.md`, brief § Permitted changes).
- **User impact:** Hits brief jobs 1 and 2 and the honesty constraint. In the Keychain-denial state (`02`, a state the index says a user reaches after rebuilding `pico`) and in the first-run state (`11`), the only on-screen statement that a row cannot be set is rendered at 1.87:1. A user with low vision or a glare-lit screen sees two rows that look empty, not two rows that say “unavailable”. Plausible impact, demonstrated measurement.
- **Recommendation:** **[polish]** — the brief explicitly permits changing “which control presents a choice”. When there is nothing to choose, stop drawing a popup: present the row as `LabeledContent` with the reason as ordinary secondary text (the treatment already used by `SettingsValueRow`, measured 3.90:1 — see ACC-5 — i.e. 2× better immediately) and keep the AX disabled semantics by adding `.accessibilityValue` plus a non-interactive presentation rather than a dimmed control. Tradeoff: the chevron is the affordance that says “this will become a menu once connected”; removing it makes the row read as permanently static, so keep the chevron in the _disabled-but-connected_ case (e.g. Reasoning level while a model loads) and drop it for the unconnected scaffold.
- **Severity / confidence:** high / high (measured) for the contrast; medium confidence that users miss it, since VoiceOver users are unaffected.
- **Validation needed:** Re-measure with Increase Contrast on (not exercised in this run per the index) — if AppKit raises disabled text to ≥ 4.5:1 there, the severity drops to medium and the fix becomes “verify, don’t change”. Also measure the active-window appearance, which no capture shows.

### ACC-3 A revealed row produces no change in the accessibility tree

- **Observation:** `diff 04-tools-light.ax.txt 07-reveal-tools-wait-light.ax.txt` → **byte-identical**; `diff 13-scratch-models-set-light.ax.txt 17-scratch-reveal-reasoning-light.ax.txt` → **byte-identical**; `01` vs `08` differ only in the toolbar Back button losing `disabled`. I ran those three diffs. So in the captured post-reveal state no element carries a selected/focused/outlined attribute, and no added text says a row was targeted. Code: `app/Shared/SettingsReveal.swift:31-47` draws the outline (a `RoundedRectangle.strokeBorder` — a shape, so the brief’s “outlined by a shape, not color alone” commitment is met visually) and sets `@AccessibilityFocusState` via `.accessibilityFocused($isFocused)`. That modifier is applied to the view returned by `settingsRow(_:)`, which for `ToolPolicyRow`, `AvailableModelRows` and `SettingsValueRow` resolves to _several_ accessibility elements rather than one (see ACC-1), so I expect the focus assignment to have no single element to land on in exactly the panes where deep links are most used.
- **Principle/source:** Apple HIG, _VoiceOver_ → Navigation: “**Inform VoiceOver when visible content or layout changes occur.** People may find an unexpected content or layout change confusing because it means their mental map of the content is no longer accurate.” https://developer.apple.com/design/human-interface-guidelines/voiceover (accessed 2026-11-07; platform design guidance, primary source). Project requirement: brief § Platform and references — “Revealed rows are outlined by a shape, not color alone, and **VoiceOver focus moves to them** (proposal 0005).”
- **User impact:** Hits brief job 5 (find any pane or setting through a `pico://settings/...` link). If the focus move does not fire, a VoiceOver user following a link gets a pane switch and a scroll with no statement of what was targeted — the entire point of the link. **Hypothesis**, not demonstrated: a static AX snapshot cannot show a focus-change notification, so the identical trees are consistent with both “focus moved” and “nothing happened”. The code pattern is what makes me suspect the latter for Tools/Models-catalog/Versions rows.
- **Recommendation:** **[polish]** — combine the targeted rows into single accessibility elements (ACC-1) so `.accessibilityFocused` has an element to bind to, and have `settingsRow` add an `.accessibilityValue` or an `AccessibilityNotification.Announcement` naming the revealed setting, so the reveal is audible and not only focus-dependent. Tradeoff: an announcement on top of a focus move can double-speak; prefer focus move first and announce only if focus cannot be placed.
- **Severity / confidence:** high / medium (code and AX evidence; behavior untested).
- **Validation needed:** With VoiceOver running, send `pico://settings/tools/wait`, `pico://settings/models/reasoning-level` and `pico://settings/general/settings-file` and record where the VoiceOver cursor lands and what is spoken. While testing, also check whether the pointer-only `Copy Path` context menu on `SettingsFileRow` (`app/Panes/SettingsFileRow.swift:39-42`) is reachable with VO-Shift-M and under Full Keyboard Access.

### ACC-4 Nothing the app does in response to a button is announced

- **Observation:** Code-derived. `grep` over `app/` for `AccessibilityNotification`, `announcement`, `NSAccessibility` returns no matches, so the app never posts an announcement or layout-change notification. The states that change in place are exactly the recovery states the index lists as not captured: `"Checking…"` / progress row with Cancel (`app/Runtime/RuntimeSection.swift`, `RuntimeActivityStatus.swift`), `"Loading…"` and `"Saving changes…"` (`app/Panes/ModelDefaultsFooter.swift:8-19`), and the updates results (`app/Runtime/RuntimeUpdatesRow.swift`). In the captured tree these are plain `AXStaticText` inside the row (`01-general-light.ax.txt:55-58` `"Updates"` / `"Not checked"`), with the triggering buttons several elements away (`01-…ax.txt:59-60` `Check Runtime`, `Check for Updates`). Search behaves the same way: typing replaces the whole sidebar list with results (`app/Navigation/SettingsSidebar.swift:13-21`) and `"No Results"` is an `.overlay` on an empty `List` (`app/Search/SearchResultsList.swift:13-18`), with no count or emptiness announced.
- **Principle/source:** Apple HIG, _VoiceOver_ → Navigation: “Inform VoiceOver when visible content or layout changes occur… It’s crucial to report visible changes so VoiceOver and other assistive technologies can help people update their understanding of the content.” https://developer.apple.com/design/human-interface-guidelines/voiceover (accessed 2026-11-07; platform design guidance, primary source). Maps loosely to WCAG 4.1.3 Status Messages.
- **User impact:** Hits brief job 1 (confirm Pico starts; recover) most directly: press _Check Runtime_, hear nothing, and the only way to learn the outcome is to navigate back through the group and re-read three rows — twice, given the duplicated values in ACC-1. Also job 5: a VoiceOver user typing in Search gets no signal that the sidebar now holds results or none. Plausible; not demonstrated.
- **Recommendation:** **[polish]** — announce the terminal state of each user-initiated check (`"Command startup: Passed"`, `"Couldn’t load settings"`, `"Saved"`) and the search result count / `"No Results"` via `AccessibilityNotification.Announcement`. Keep it to terminal states only. Tradeoff: announcing intermediate `"Checking…"` as well would interrupt a user mid-navigation, so announce start only for operations long enough to need it and let the progress row carry the rest.
- **Severity / confidence:** medium-high / medium (absence of the API is certain; whether macOS VoiceOver already speaks some of these changes on its own is not).
- **Validation needed:** With VoiceOver on, press _Check Runtime_ and _Try Again_ from the failing state and record what, if anything, is spoken before and after the change; type a query and listen for a result count.

### ACC-5 In Light appearance, the text carrying each row’s status sits at 3.90:1 — and the warning state has no non-text marker

- **Observation:** Measured from `01-general-light.png`: `"Installed"`, `"Not checked"`, `"Not connected"` (Versions), the settings-file path and `"Couldn’t load"` all resolve to #7C7C7C on #F7F7F7 = **3.90:1**; the matching row labels are 14.13:1. The same strings in `45-providers-dark.png` measure #9D9D9D on #252525 = **5.65:1**, and the dark footnote 5.92:1 — so the identical information is compliant in Dark and not in Light. Code: `app/Shared/SettingsValue.swift:18-24` and `app/Runtime/RuntimeCheckRow.swift:21` set `.foregroundStyle(.secondary)` on the value, i.e. the status is always the _lighter_ of the two texts in its row. Separately, I opened `14-scratch-models-saved-unavailable-light.png` and `13-scratch-models-set-light.png` side by side: the critical warning “New sessions will fail to start until you choose an available model and level” is rendered in exactly the same secondary gray, weight and position as the benign footer “Pico uses this model and reasoning level for new sessions…”, with no icon, no color and no weight change — even though the app already owns a warning idiom (`exclamationmark.triangle` in `RuntimeCheckRow.swift:16` and `ModelsPane.swift:18`). `grep` finds no use of `colorSchemeContrast` anywhere in `app/`, so the app relies entirely on system colors for Increase Contrast — correct platform behavior, but unverified.
- **Principle/source:** Apple HIG, _Accessibility_ → Vision: 4.5:1 for text up to 17 pt, all weights; “make sure to check the minimum contrast in both light and dark appearances”; “**Prefer system-defined colors** … they automatically adapt when people enable Increase Contrast”; “**Convey information with more than color alone** … Offer visual indicators, like distinct shapes or icons.” https://developer.apple.com/design/human-interface-guidelines/accessibility (accessed 2026-11-07; primary source). WCAG 2.2 SC 1.4.3 (AA) is the mapped testable criterion for the 3.90:1 figure.
- **User impact:** Job 1 (read runtime state at a glance) and job 2 (notice that the saved default is broken). `.secondary` is Apple’s own color and System Settings uses it the same way, so this is a platform-inherited shortfall rather than a local mistake — but the _warning/benign_ indistinguishability in `13` vs `14` is a local choice, and it is the one a scanning user actually pays for. Plausible impact; measurement demonstrated.
- **Recommendation:** **[polish]**, two parts, smallest first: (a) give every warning/failure footer the same leading `exclamationmark.triangle` the row-level failures already use, so `14` is distinguishable from `13` without reading the sentence; (b) for failure and “action needed” statuses only, promote the value from `.secondary` to `.primary` (14.13:1), keeping `.secondary` for neutral values like paths and versions. Tradeoff: (b) departs slightly from System Settings’ uniform secondary values and adds visual weight to the exact rows the Perception lens may want quiet — worth raising at deliberation rather than applying unilaterally. Do not hand-roll a contrast palette; `colorSchemeContrast` should stay unused.
- **Severity / confidence:** medium / high for the numbers, medium for the impact.
- **Validation needed:** Re-measure Light appearance with Increase Contrast on; if AppKit lifts `secondaryLabelColor` to ≥ 4.5:1 there, part (b) becomes unnecessary and only (a) stands. Separately: the sidebar labels in `11-scratch-models-not-set-light.png` measure #8C8C8C on #F2F2F2 = **3.00:1** and the Models badge “1” = **2.35:1**, but the index states every capture is the **inactive**-window appearance, and sidebar text is activity-dependent — these two numbers must be re-measured on an active window before anyone acts on them. I did not verify the active appearance.

## Worth keeping

- **The unconnected rule is honored for assistive clients, not just visually.** Every scaffold row carries a literal `"Not connected"` value and every dead control is exposed as `disabled` in the tree — `01-general-light.ax.txt:73-80` (Versions), `03-providers-light.ax.txt:45-48` (`Add Provider…` disabled), `05-sesh-light.ax.txt:54-59` (`Register` disabled), `02-models-light.ax.txt:43-46` (both popups disabled). No pane fakes a capability to VoiceOver. Keep this exactly as is.
- **Decorative art is hidden and meaningful text is not.** `app/Shared/AppIconTile.swift:23` hides the colored pane tiles and `app/Runtime/RuntimeCheckRow.swift:17` hides the warning triangle whose meaning is already in the adjacent text — so no outline contains a stray image announcement. This is the HIG’s “Exclude purely decorative images from VoiceOver” done correctly.
- **Retained panes do not leak phantom elements.** `app/Navigation/RetainedSettingsPanes.swift:12-13` disables _and_ `accessibilityHidden`s every non-selected pane; the outlines confirm only one pane’s content is present at a time. Keep both modifiers paired — dropping the `accessibilityHidden` would put six panes of duplicate rows in the tree.
- **Reduce Motion already gates the reveal scroll** (`app/Panes/SettingsPane.swift:14-17`: unanimated `scrollTo` when `accessibilityReduceMotion` is set), and the sidebar badge carries words rather than a bare count (`app/Navigation/DestinationList.swift:34` → `11-scratch-models-not-set-light.ax.txt:19` `description="Models" value="Default model not set"`). Both are the right instinct; extend the badge pattern rather than replacing it.

## Lens score

**6/10.**

Rubric factors I used, with what each contributed. _Names and roles_ (strong): every control in every outline has a description and correct role — popups, buttons, disclosures, the search field and the toolbar segments all carry labels, and none are generic. _States_ (strong): `disabled` is exposed everywhere it should be, and “Not connected” is a real value rather than an empty string. _Relationships and structure_ (weak, −2): the Default marker, the tool verdicts, the Versions values and the Sesh Register button are associated by position only, three different grouping idioms coexist for one visual row pattern, and four sidebar rows have no name (ACC-1). _Change and focus reporting_ (weak, −1.5): no announcement API is used anywhere, and the captured reveal produces no tree change (ACC-3, ACC-4). _Contrast_ (mixed, −0.5): Dark passes comfortably; Light sits at 3.90:1 for status values and 1.87:1 for the unavailable state that the brief insists must stay visible (ACC-2, ACC-5). _Motion and decoration_ (strong): Reduce Motion handled, decorative images hidden.

What I could not assess, and what would move this score: **no VoiceOver was run**, so every claim about what is spoken is inference from tree shape and code; keyboard-only traversal and Full Keyboard Access were not exercised; Increase Contrast was not exercised, and it could raise both contrast findings out of range; the active-window appearance is not in evidence, which invalidates my sidebar and badge measurements until re-taken; loading, saving, updates-result, Homebrew-confirmation, expanded-Error-Details, empty-catalog, search-results and alert states were never captured, so their accessibility is entirely unexamined here; localization and larger text sizes were not examined at all. This score describes how the app represents itself in the captured states only. **It is not a conformance result**, and ACC-1 and ACC-2 should be treated as open regardless of how the council votes.

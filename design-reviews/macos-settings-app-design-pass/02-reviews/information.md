# Information and content review

Reviewer: Information and content. Brief version 1. Evidence: index of 2026-11-07.

## Findings

### INF-1 “Not connected” is both the scaffold placeholder and a believable real status, so Sesh states facts the app never checked

- **Observation:** I opened `01-evidence/before/05-sesh-light.png` and inspected the inactive-window Sesh pane. Under the heading **Connection**, the row **Sesh custom agent** reads “Not connected” with a disabled **Register** button beside it, and **Connection status** reads “Not connected”. Under **Setup**, **Setup status** reads “Not connected”. The same words appear in `05-sesh-light.ax.txt` lines 53–65 as bare row values with no qualifier. Code: `app/Shared/SettingsValue.swift:17` emits `Text("Not connected")` for _every_ row whose value is `nil`, and `app/Panes/SeshPane.swift:9–30` passes `value: nil` for all five Sesh rows — so the identical string stands for “the app has not looked” on the Versions rows (`01-general-light.png`, Versions group) and for a plausible connection verdict on the Connection rows. The only correction is the section footer, `app/Panes/SeshPane.swift:26`: “Nothing is read from Sesh, and no registration is inspected.” A third footer (line 34) says “Guided setup through Sesh is not available from this scaffold” — “scaffold” is implementation vocabulary that reached a shipping string (`app/Localizable.xcstrings:103`).
- **Principle/source:** Apple HIG, _Writing_ — “Create a list of common terms, and reference that list to keep your language consistent”; “Choose words that are easily understood and convey the right thing”; avoid jargon (vendor guideline, https://developer.apple.com/design/human-interface-guidelines/writing, accessed 2026-11-07). NN/g, _Match Between the System and the Real World_ — speak the user’s language, not system-oriented terms (research synthesis, https://www.nngroup.com/articles/match-system-real-world/, accessed 2026-11-07). Rosenfeld, Morville & Arango, _Information Architecture: For the Web and Beyond_, 4th ed., ch. 6 on labeling systems: one label should carry one meaning (book). The brief’s own success condition requires that “unconnected scaffolding [is] honest and distinguishable”.
- **User impact:** Demonstrated at the string level for the brief’s “not yet connected” rule: a sighted reader scanning the Connection group, and a VoiceOver user hearing “Connection status, Not connected” (AX outline 05, lines 57–59), both receive a measured-sounding verdict about Sesh. Plausible task impact: a user who has in fact registered Pico in Sesh reads this pane as evidence that registration is broken and goes looking for a fault that does not exist. “Setup status — Not connected” is also not idiomatic English for a status.
- **Recommendation:** **[polish]** Split one word into two meanings. Keep “Not connected” only where it means _the app does not read this yet_, and give rows whose names already denote a connection or a state a placeholder that cannot be mistaken for a measurement — e.g. em-dash/“—” plus the existing footer, or “Not checked here”. Rename the three Sesh rows to name the _thing_ rather than its state (“Custom agent”, “Connection”, “Setup”) so the value column is unambiguously a placeholder. Replace “from this scaffold” with the vocabulary used by the neighbouring footers (“…is not available here”), and align the three footers on one pattern; today they vary between “is not resolved while settings stay unconnected”, “Nothing is read from Sesh…”, and “…from this scaffold”. Tradeoff: a dash is less explicit than a sentence for someone who skips the footer, so the footer must stay.
- **Severity / confidence:** high / high
- **Validation needed:** A five-minute first-read test: show the Sesh pane and ask “has Pico been registered in Sesh?” A correct answer is “the app doesn’t say”. Repeat with VoiceOver row-by-row navigation, since the footer is a separate element.

### INF-2 The settings file’s health is reported on Models, while General — the pane that owns the file — says nothing is wrong

- **Observation:** I opened `01-evidence/before/16-scratch-models-invalid-file-light.png`: with an unparseable `settings.json`, Models shows, as secondary gray text under the Defaults group, `$: not JSON: JSON Parse error: Unexpected EOF`, then “Fix or remove this settings file before changing model defaults.”, then **Show in Finder…**. The phrase “this settings file” has no antecedent on that pane — the path is not shown there. For the same profile state, `15-scratch-general-invalid-file-light.ax.txt` lines 63–68 show General’s **Settings file** row with only **Show in Finder…** and the path, and the footer “Pico’s settings are separate from your OMP configuration.” — no problem reported at all. Code: `app/Panes/ModelDefaultsFooter.swift:15` carries the “Fix or remove…” sentence; `app/Panes/GeneralPane.swift:12–18` has no invalid-file branch. The General pane’s own summary promises the opposite ownership: “Check the Pico command and find its settings file.” (`app/Navigation/SettingsDestination.swift:48`).
- **Principle/source:** NN/g, _Error-Message Guidelines_ — “Display the error message close to the error’s source”; “Use human-readable language… Hide or minimize the use of obscure error codes”; “Concisely and precisely describe the issue” (research synthesis, https://www.nngroup.com/articles/error-message-guidelines/, accessed 2026-11-07). Apple HIG, _Writing_ — “display it as close to the problem as possible… be clear about what someone can do to fix it” (vendor guideline, URL above, accessed 2026-11-07).
- **User impact:** Hits the brief’s core job 3 (“Find the settings file”) and, through it, job 2. Demonstrated: the two captures show that the pane a user goes to for the settings file is silent about the file being broken, while the diagnosis sits on an unrelated pane. Plausible: a user who opens General to check configuration, sees a healthy-looking path, and then cannot change a model has no route from the symptom to the cause except visiting Models by chance. The raw string `$: not JSON: JSON Parse error: Unexpected EOF` leads with a JSON-pointer artefact (`$:`) that means nothing outside the parser.
- **Recommendation:** **[polish]** On Models, label the raw text rather than leading with it: a one-line human statement (“Pico couldn’t read the settings file.”) with the parser message demoted into the existing **Error Details** disclosure pattern already used in General (`01-general-light.png`, “Error Details”), and name the file by path or at least by name next to **Show in Finder…**. **[proposal]** Also surface the invalid-file state on General’s **Settings file** row, so the pane that owns the file reports its condition; this changes what the user can find out there, so it needs a decision rather than a wording edit. Tradeoff: duplicating the state in two panes risks the drift described in INF-3, so one of the two should be the primary and the other a short pointer.
- **Severity / confidence:** high / high
- **Validation needed:** With an invalid `settings.json`, ask a participant starting on General to explain why they cannot change the default model, and time how long it takes to reach **Show in Finder…**.

### INF-3 Versions exist twice, under two different label systems, two different explanations, and the same slugs

- **Observation:** I inspected `01-general-light.png` and `06-diagnostics-light.png`. General ends with a **Versions** group: **Pico app**, **pico** (monospace), **OMP**, each “Not connected”, footer “Installed versions are not read here.” Diagnostics & About opens with an **About** group containing **App version**, **pico version**, **OMP version**, each “Not connected”, footer “Installed versions are not read while settings stay unconnected.” Confirmed in `01-general-light.ax.txt` lines 70–81 and `06-diagnostics-light.ax.txt` lines 42–54. Code: `app/Settings/SettingsItem+Catalog.swift` defines both sets, and both use the slugs `app-version`, `pico-version`, `omp-version` — so `pico://settings/general/app-version` and `pico://settings/diagnostics/app-version` are two distinct, identically named links. In General the group occupies the final third of the pane (measured against the capture: three rows plus header and footer, below the live Configuration group). Searching “version” matches seven locations (`upToDate` plus all six version rows) because every one carries the title word or the keyword `version` (`SettingsItem+Catalog.swift`), and `app/Search/SearchResultsList.swift:30–36` disambiguates results only by the pane name beneath the title.
- **Principle/source:** Rosenfeld, Morville & Arango, _Information Architecture: For the Web and Beyond_, 4th ed. — labeling systems must be internally consistent; the same content under two labels in two categories destroys predictability (book). Krug, _Don’t Make Me Think_, on omitting needless words and on self-evident labels (book). Apple HIG, _Writing_ — “Build language patterns. Consistency builds familiarity”; “Check each word to be sure it needs to be there” (vendor guideline, URL above, accessed 2026-11-07).
- **User impact:** Affects job 1 (General’s legibility) and job 5 (finding things). Demonstrated from the captures and the catalog: the busiest pane ends with three rows that report nothing, and the pane explicitly titled “…& About” repeats them with different names, so neither pane is the answer to “where do I look up versions?”. Plausible: a user searching “version” gets a result list of near-duplicates (“Pico app · General”, “App version · Diagnostics & About”, “pico · General”, “pico version · Diagnostics & About”) whose only differentiator is the pane, and every one of them is inert.
- **Recommendation:** **[proposal]** Keep versions in one place — Diagnostics & About, which its summary already claims (“Versions, recent errors, and reports for troubleshooting.”) — and drop the General group; that removes rows and link targets, so it is a decision, not a wording edit. **[polish]** If both must stay, make them identical: one label set (“Pico app”, “`pico`”, “OMP” under a **Versions** header in both), one footer sentence, and rename Diagnostics’ **About** header to **Versions** so the section header matches its own pane summary. Tradeoff: moving versions out of General lengthens the path for a user who expects “About”-style facts on the first pane; the sidebar and search still reach them in one step.
- **Severity / confidence:** high / high
- **Validation needed:** Ask five developers “where would you look up which version of `pico` is installed?” before opening the app (first-click test on the sidebar), then check whether the result list for “version” lets them pick confidently.

### INF-4 One object has six names, and “Installed” means two different things in adjacent rows

- **Observation:** Across the captures, the local `pico` executable is called: **Runtime** (section header and the **Check Runtime** button, `01-general-light.png`); **Installation** (row, same capture); **Command startup** / “Command version: 0.1.0” / “Command startup checks Pico…” (same capture and `01-general-light.ax.txt` lines 50–61); **pico** (Versions row, monospace); **Pico** (pane summary “Check the Pico command…”); **Helper location** (`05-sesh-light.png`, and `proposals/0005-mac-app-ui-workspace.md:117` confirms the helper is `/opt/homebrew/bin/pico`); and **the Pico ACP adapter** (`06-diagnostics-light.png`, “Native configuration for the Pico ACP adapter.”). “Helper” appears nowhere else in the app. Code-derived: `app/Runtime/RuntimeUpdatesRow.swift` gives the row titled **Updates** twelve values, six of which are not about updates — “Not installed”, “Not linked”, “Custom executable”, “Homebrew not found”, “Homebrew needs updating”, “Trust required” — so the pane can simultaneously read _Installation: Installed_ (`RuntimeInstallationRow.swift:14`) and _Updates: Not installed_ (`RuntimeUpdatesRow.swift:31`). These update states are listed as “Not captured” in the evidence index, so this is a code claim, not an observed screen. Search inherits the drift: the keyword `runtime` is attached to **Installation**, **Command startup**, **Updates** and **pico** (`SettingsItem+Catalog.swift`), so typing “runtime” returns four results, none of whose visible names contains the word. In Tools (`04-tools-light.png`) the engine terms **Eval**, **Built-in LSP**, **Native delegation** and “the intellisense program” appear with no gloss, although `guides/refining-the-mac-app-ui.md:97` glosses most of them.
- **Principle/source:** Apple HIG, _Writing_ — “Create a list of common terms, and reference that list to keep your language consistent”; “Keep settings labels clear and simple… If the setting label isn’t enough, add an explanation” (vendor guideline, URL above, accessed 2026-11-07). NN/g heuristic #2 — avoid system-oriented terms and unexplained acronyms (research synthesis, URL above, accessed 2026-11-07). Rosenfeld et al., ch. 6 (book).
- **User impact:** Affects jobs 1, 3, 4 and 5. Demonstrated from the captures that four names for the same object appear within one scroll of General. Plausible and, for the Updates row, specific: a user recovering a broken install reads “Installation — Installed” and “Updates — Not installed” on consecutive rows and cannot tell which is true; the two sentences are about different systems (the file on disk vs. Homebrew’s record) but share a word.
- **Recommendation:** **[polish]** Pick one user-facing name for the object — the brief’s user installs it with Homebrew and types it, so **the `pico` command** is the honest choice — and apply it everywhere: section header “Runtime” → “Pico command”; button “Check Runtime” → “Check Again” or “Check Command”; Sesh’s “Helper location” → “`pico` location”; keep “Pico” for the app. **[polish]** Reword the Updates row’s Homebrew-state values so they do not re-use “installed”: “Not in Homebrew”, “Command link missing”, “Homebrew not found”, “Homebrew needs updating”, “Needs your permission”. **[proposal]** Add a one-line gloss under each tool name in Tools (the guide’s text already exists), since that changes what the user can find out. Tradeoff: “Runtime” is the vocabulary of the proposals and of `PROTOTYPE.md`; renaming it in the UI makes the app and its internal docs disagree until the docs follow.
- **Severity / confidence:** medium / high for the naming spread (captures); medium for the Updates-row collision (code only, state not captured)
- **Validation needed:** Build the Updates states listed in the evidence index as “not captured” and screenshot each; then ask a participant holding a working install to read General aloud and say how many separate programs the pane is describing.

### INF-5 Search and links lose plausible queries: word-prefix matching, slug/label drift, and a dead-end alert

- **Observation:** Code: `app/Search/SettingsSearch.swift:17–21` matches only when a query word is a **prefix of a whole candidate word**. The `installed` item’s keywords are `["runtime", "readiness", "pico", "Homebrew", "installed"]` (`SettingsItem+Catalog.swift`), so typing **`brew`** — the name of the command the user actually runs, and the tool behind every recovery action in the brief’s job 1 — returns “No Results” (`SearchResultsList.swift:14–17`), while “homebrew” works. No item carries `json`, although the thing being sought is `settings.json`. Link vocabulary drifts from labels: slug `up-to-date` for the row titled **Updates**, `starts` for **Command startup**, `installed` for **Installation**, `custom-agent` for **Sesh custom agent**, `app-version` for **Pico app** (all in `SettingsItem+Catalog.swift`; slugs are frozen by the brief, titles are not). A guessed link such as `pico://settings/general/updates` therefore fails, and the failure is a dead end: `app/Navigation/SettingsWindowView.swift:57–65` shows “Pico Can’t Open This Link” / “‘…’ doesn’t name a pane or setting in Pico.” with a single **OK** — I inspected `32b-rejected-link-alert-panel.png` and `32-rejected-link-alert-680.png` and the alert offers no way to discover a valid name. Search results themselves cannot be captured (evidence index, “Not captured”), so the result-list claims are code-derived.
- **Principle/source:** NN/g, _Error-Message Guidelines_ — “Offer constructive advice… Merely stating the problem is not enough” and “Reduce error-correction effort” (research synthesis, URL above, accessed 2026-11-07). GOV.UK design principles #4, _Do the hard work to make it simple_, and #10, _Make things open_ (government guidance, https://www.gov.uk/guidance/government-design-principles, accessed 2026-11-07). Rosenfeld et al. on synonym rings / controlled vocabularies in search systems (book).
- **User impact:** Job 5 directly, and job 1 indirectly. Demonstrated from code that “brew” yields nothing. Plausible: a developer recovering a broken install types the word they type in Terminal and concludes the app has no Homebrew controls, when **Check for Updates** and the recovery buttons are one pane away.
- **Recommendation:** **[proposal]** Add the few missing synonyms a user is likely to type — `brew` on **Installation** and **Updates**, `json` and `settings.json` on **Settings file**, `updates` on the row whose slug is `up-to-date` — and consider substring matching for queries of four or more characters; both change what can be found, so they are decisions, not wording edits. **[polish]** Make the rejected-link alert end somewhere: name the valid pane slugs in the message (they are fixed and public) or change the button to open Pico on General rather than only dismissing. Tradeoff: substring matching returns more and fuzzier results in a 29-item catalog; the keyword additions alone may be sufficient and are far cheaper.
- **Severity / confidence:** medium / medium (behaviour read from source and from `SettingsSearchTests.swift`’s scope, not observed on screen)
- **Validation needed:** Capture the search results list for `brew`, `homebrew`, `version`, `runtime`, `json` and `update` — this needs a capture method that does not steal the user’s focus — and run a short findability test: give five target settings and record query words and success rate.

## Worth keeping

- **One source for labels and search terms.** `app/Settings/SettingsItem+Catalog.swift` states it outright (“Every row label in the panes comes from here, and so does every search match, so a row and its search result cannot disagree”). This structurally prevents the most common settings-search defect; keep it as the place any relabeling happens.
- **Per-section footers that say what the app does _not_ do.** “No diagnostics are collected, redacted, or exported here.” (`06-diagnostics-light.png`), “Supported providers come from the engine; none are listed here.” (`03-providers-light.png`), “Command startup checks Pico, not provider sign-in or a model turn.” (`01-general-light.png`). Negative scope statements are rare and genuinely useful; the pattern should survive even where the wording is tightened.
- **The pane header card: title plus one plain sentence.** Every capture opens with the sidebar tile, the pane name and a one-line summary (`SettingsDestination.summary`). It answers “what is this pane for?” before any row is read, and the summaries are written in user terms, not feature terms.
- **Available Models showing both the display name and `provider/id`, with a “Default” marker.** `13-scratch-models-set-light.ax.txt` lines 50–57. It reconciles the friendly name in the picker with the identifier stored in settings — exactly the bridge a developer needs — and names the saved choice instead of relying on selection styling.
- **Status that names itself in the sidebar badge.** `11-scratch-models-not-set-light.ax.txt` line 19 gives the Models badge the value “Default model not set” rather than a bare “1”. That is the right instinct and should be the model for every other status this review asks to be rewritten.

## Lens score

**6/10.** Rubric factors I used: (1) findability — can a user predict which pane holds a thing, and does search/link vocabulary match the labels; (2) labeling consistency — one concept, one label, one meaning; (3) content placement — is each fact where its owning task lives; (4) honesty and precision of status and error copy; (5) economy — does any screen spend space on words that carry no information.

The structure scores well: six well-named panes in a sensible grouped sidebar, a one-line purpose statement on every pane, a single catalog behind labels and search, and a deliberate habit of stating what the app does not do. The deductions are all in vocabulary and placement, not in architecture: a single placeholder string (“Not connected”) doing duty as a real status (INF-1); the settings file’s condition reported on a pane that does not show the file (INF-2); one body of content duplicated under two naming systems with colliding slugs (INF-3); the product’s central object carrying six names, with “installed” meaning two different things on adjacent rows (INF-4); and a search/link vocabulary that drops plausible queries with no recovery (INF-5).

What I could not assess: search results and “No Results” were never captured (evidence index), so every claim about the result list is read from `SettingsSearch.swift` and `SearchResultsList.swift`; loading, saving, Homebrew-confirmation, expanded Error Details and all twelve Updates results are likewise code-only; the active-window appearance, localization, Increase Contrast and real VoiceOver speech were not exercised in this run; and with no user research, every statement here about what a user expects a label to mean is a hypothesis, not a finding about users.

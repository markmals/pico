# Tasks and interaction review

Reviewer: tasks and interaction. Brief version 1. Evidence: index of 2026-11-07.

## Findings

### INT-1 A Homebrew recovery runs with no stop, and closing the window kills it without warning

- **Observation:** Code-derived; no capture exists for this state (the evidence index lists Homebrew confirmations and the progress row as “not captured”). `app/Runtime/RuntimeSection.swift:33-45` shows a Cancel button only for `.checking` and `.checkingUpdates`; for `.running(action)` and `.stopping` it renders `EmptyView()`. The package action is the long one: `PicoRuntimeClient.swift:75` allows `actionTimeout = 1800` seconds, against 120 s for inspection. Feedback during those 30 minutes is one indeterminate `ProgressView` plus a fixed string such as “Installing Pico…” (`RuntimeActivityStatus.swift:15-21`); Homebrew’s own progress output is captured but never shown (`PicoRuntimeClient.swift:69` keeps a 64 KB tail). Meanwhile the only way to stop the action is to leave: `PicoApp.swift:15-20` declares a single `Window`, `RuntimeTerminationDelegate.swift:21-23` returns `true` from `applicationShouldTerminateAfterLastWindowClosed`, `SettingsWindowView.swift:48-51` calls `runtime.cancel()` in `onDisappear`, and `RuntimeTerminationDelegate.swift:10-19` calls `cancelAndWait()` on quit — so ⌘W or ⌘Q terminates `brew` (the whole process group, per the comment in `HomebrewCommand.swift:67-69`) with no confirmation. The app itself treats interruption as consequential: the reinstall confirmation says “Stop sessions using this installation, and do not start another until it finishes” (`HomebrewAction+Presentation.swift:26-27`). Navigating to another pane also hides the progress row entirely, since it lives inside `GeneralPane` (`GeneralPane.swift:10`) and panes are stacked by opacity (`RetainedSettingsPanes.swift:7-16`).
- **Principle/source:** Apple HIG, _Progress indicators_ — “When it’s feasible, let people halt processing… If interrupting the process might cause negative side effects — such as losing the downloaded portion of a file — it can be useful to provide a Pause button in addition to a Cancel button,” and “Let people know when halting a process has a negative consequence… provide an alert that includes an option to confirm the cancellation or resume the process” (first-party guidance, https://developer.apple.com/design/human-interface-guidelines/progress-indicators, accessed 2026-11-07). Nielsen heuristic #3, user control and freedom: “a clearly marked emergency exit” (research synthesis, https://www.nngroup.com/articles/ten-usability-heuristics/, accessed 2026-11-07). The project guide already commits to this for the cheap half only: “Local and update checks show progress and can be cancelled” (`guides/refining-the-mac-app-ui.md:37`).
- **User impact:** Task 1 (“recover through confirmed Homebrew actions”). Demonstrated from code: the longest, most consequential operation is the only one without an exit, and the cheapest exit a Mac user reaches for — closing the window — silently becomes the kill switch. Plausible consequence: an interrupted `brew install`/`reinstall` leaves the user’s command in a state neither they nor the app described, exactly the “silent failure” the brief forbids elsewhere.
- **Recommendation:** **[proposal]** Give the running action the same Cancel the checks have, and make leaving explicit: an alert on window close/quit while `activity == .running` offering “Keep Installing” / “Stop”. **[polish]** within the same row, replace the bare spinner with the action’s current Homebrew step (the tail output is already retained) so a four-minute download does not look stalled. Tradeoff: a close-time alert is friction on a window users expect to dismiss freely, and showing brew output costs vertical space in a 680 pt-tall default window.
- **Severity / confidence:** high / medium (every mechanism is read from source; the damage from an interrupted `brew` is inferred, not observed).
- **Validation needed:** Run an install against a slow formula, confirm no Cancel appears, then press ⌘W and check `brew list --versions pico` and Homebrew’s lock state. Re-check whether `cancel()` during `.running` is even safe to expose before shipping the button.

### INT-2 The sidebar badge flags the harmless state and stays silent on the two broken ones

- **Observation:** I opened `11-scratch-models-not-set-light.png` and `14-scratch-models-saved-unavailable-light.png`. In 11 — no saved default, a working fallback named in the footer (“Until you choose a model, Pico uses lm-studio/qwen/qwen3-coder-30b…”) — the Models row carries a prominent “1” badge, and `11-…ax.txt:19` gives it the value “Default model not set.” In 14 — footer reads “The saved model or reasoning level is unavailable. **New sessions will fail to start** until you choose an available model and level” — there is no badge, and `14-…ax.txt:19` carries no accessibility value at all. The same silence covers `02-models-light.png` (load failed, both pickers “Unavailable”) and `16-scratch-models-invalid-file-light.png` (unparseable settings file). The rule is in `app/Navigation/DestinationList.swift:32-39`: the badge fires only when `displayedDefaults` exists and `defaultModel == nil`, and `displayedDefaults` is `nil` for `.loading`, `.failed` and `.invalid` (`ModelSettings.swift:20-26`). So the single attention signal in the window is awarded to the state where Pico still works and withheld from every state where it does not.
- **Principle/source:** Nielsen heuristic #1, visibility of system status — “no action with consequences to users should be taken without informing them” (research synthesis, URL above, accessed 2026-11-07). Norman, _The Design of Everyday Things_ (rev. ed., MIT Press, 2013), on feedback that must be proportionate to consequence — an over-firing signal is learned as noise. Book.
- **User impact:** Task 2, and task 1 by extension: General is the pane the window opens on (`SettingsNavigator.swift:17`), so a user who never clicks Models gets a badge when nothing is wrong and nothing when new sessions are about to fail. Demonstrated for sighted users and VoiceOver alike from captures 11/14 and their AX outlines.
- **Recommendation:** **[proposal]** Make the badge mean “this pane needs attention”: saved-but-unavailable model, load failure, and invalid settings file, with accessibility values that name the state (“Saved model unavailable”, “Couldn’t load model settings”). **[polish] fallback if the proposal is deferred:** keep the current trigger but stop styling it as an alert — `.badgeProminence(.increased)` reads as an error marker for a condition the footer describes as working. Tradeoff: badges that fire on transient load failures could flicker during reloads; gate on a settled state, not on `.loading`.
- **Severity / confidence:** high / high (two captures plus both AX outlines plus the rule in source).
- **Validation needed:** Confirm the badge does not flash during the reload that `SettingsWindowView.swift:52-55` triggers on every return to Models; check with VoiceOver that the new values are announced on the sidebar row.

### INT-3 When the settings command fails, the pane that exists to find the settings file stops naming it

- **Observation:** I opened `01-general-light.png` (Real profile, the state Mark’s Mac is in today per the evidence index). The Configuration group shows “Settings file — ⚠ Couldn’t load — Try Again” and a collapsed “Error Details”; the path appears nowhere in the window, and `01-…ax.txt:63-68` confirms the row contains only the label, the status, the button and the disclosure. `30-missing-exec-general-680.png` is the same. The path is only ever known if `pico settings get` answers (`PicoSettingsRead.swift:20`, `ModelSettings.swift:154-159`), and when it doesn’t, “Copy Path” in the row’s context menu is disabled too (`SettingsFileRow.swift:39-42`). The only offered action, Try Again, re-runs the identical command; the evidence index records this particular failure as deterministic and reproducible (`KEYCHAIN_ACCESS_DENIED`, −25293). The cause is one disclosure click away and arrives as raw CLI text (`CommandErrorDetails.swift:19-27`, `PicoCommandError.swift:13`) — in capture 16 that text reads “$: not JSON: JSON Parse error: Unexpected EOF”, i.e. an error code style message with no suggested action. Nothing in General or Models connects this failure to the Runtime section directly above it, where the real fix lives when `pico` is missing.
- **Principle/source:** Nielsen heuristic #9 — error messages should “precisely indicate the problem, and constructively suggest a solution,” in plain language, no codes (research synthesis, URL above, accessed 2026-11-07). Shneiderman’s golden rule 7, “permit easy reversal of actions”/rule 5 “offer simple error handling” (https://www.cs.umd.edu/~ben/goldenrules.html, accessed 2026-11-07). Krug, _Don’t Make Me Think_ (rev. ed., New Riders, 2014): a dead end that repeats itself trains users to stop trying. Book. The project guide accepts the behavior (“If the settings command itself fails, General shows Couldn’t load and Try Again”, `guides/refining-the-mac-app-ui.md:93`), so this is a design question, not a defect.
- **User impact:** Task 3 fails outright in the captured real-profile state: the pane subtitled “Check the Pico command and find its settings file” can no longer tell the user where the file is, and offers one button that will fail again. Demonstrated. Task 1 is affected too: a failure caused by the runtime is reported in Configuration with no pointer to Runtime.
- **Recommendation:** **[polish]** Make the failed row carry the next step instead of a bare retry: expand Error Details by default in the failure state (the layout already reserves room and scrolls long text, `CommandErrorDetails.swift:8-15`), and add one sentence of non-requirement wording naming where to go — e.g. that Pico reads the location by running `pico`, so the Runtime checks above come first. Surface “Copy Path” as a visible control rather than a context menu documented only in the guide (`guides/refining-the-mac-app-ui.md:91`). **[proposal]** if the council wants task 3 to survive a failure: show the last known location labelled as last known, or read the location through a path that does not touch the Keychain — not an invented default, which the brief forbids. Tradeoff: an always-expanded error consumes the space the Versions group now occupies.
- **Severity / confidence:** high / high (capture 01, capture 30, and the source of the state machine).
- **Validation needed:** Reproduce the Keychain denial, press Try Again three times, and confirm no new information appears; check the expanded Error Details text against heuristic #9 wording.

### INT-4 A broken settings file is a dead end in Models and invisible in General

- **Observation:** I opened `16-scratch-models-invalid-file-light.png` and `15-scratch-general-invalid-file-light.png`, same scratch profile, same broken `settings.json`. Models shows both pickers disabled (“Unavailable”), the raw parse message, “Fix or remove this settings file before changing model defaults,” and a “Show in Finder…” button sitting outside the grouped box in the section footer — and **no Try Again**, unlike the `.failed` state in capture 02 which has both a warning icon and a Try Again. That matches the code: `ModelsPane.swift:13-27` builds the error row with Try Again only for `.failed`, and `ModelDefaultsFooter.swift:12-17` handles `.invalid` as footer prose. The only reload for this state is the implicit one in `SettingsWindowView.swift:52-55` when the destination changes to `.models`, which the user must discover by leaving and coming back. Meanwhile capture 15 — General with that same broken file — is pixel-for-pixel the same Configuration group as the healthy capture 12: path, “Show in Finder…”, no warning, because `SettingsFileRow.swift:27-34` renders `.known(path)` for `.invalid` and shows error detail only for `.failed`. A second, quieter version of the same split: in capture 10 the file does not exist yet and the row looks identical to capture 12, where it does; `ShowSettingsFileButton.swift:13-32` silently opens the containing folder instead of selecting the file.
- **Principle/source:** Nielsen heuristic #4, consistency and standards — users should not have to wonder whether two presentations of the same fact mean the same thing; and #9 on offering a solution (research synthesis, URL above, accessed 2026-11-07). Norman on the gulf of evaluation: the user must be able to tell, from the interface, what state the system is in. Book, _The Design of Everyday Things_.
- **User impact:** Tasks 2 and 3. A user who hand-edits `settings.json` — the exact user the Configuration section is built for — breaks it, is told in Models to fix it, fixes it, and then has no visible way to re-read it; and if they check General first, General tells them the file is fine. Demonstrated by captures 15/16 plus source; the user’s likely next move (quit and relaunch) is plausible, not observed.
- **Recommendation:** **[proposal]** Treat `.invalid` as a failure state with the same controls as `.failed`: a Try Again (or Reload) beside the message in Models, and a status on General’s Settings file row that says the file was found but could not be read. **[polish]** Present the parse message as a cause under the existing warning treatment rather than as footer prose, name the file in the sentence, and move “Show in Finder…” into the row where capture 12 already puts it. Tradeoff: a second status vocabulary on the settings-file row (found / unreadable / unknown) is more to localize and more to keep honest.
- **Severity / confidence:** high / high (two captures plus the two view files).
- **Validation needed:** Break `settings.json`, confirm no reload control appears in Models; fix it and time how long it takes a fresh user to realise they must switch panes. Confirm whether `.invalid` should also disable the General row’s “Show in Finder…”, or keep it as the fix path.

### INT-5 Search is the entry to task 5, but it has no keyboard route in and no forgiveness for exact terms

- **Observation:** Code and project-guide derived; search results could not be captured (evidence index). Two gaps. (a) There is no Find command: `SettingsCommands.swift` replaces only `.appSettings` and `.sidebar`, and the guide states the limit outright — “There is no keyboard shortcut for the search field” (`guides/refining-the-mac-app-ui.md:134`) — while the brief lists keyboard navigation as required support. (b) `SettingsSearch.matches` requires _every_ query word to be a prefix of some candidate word (`SettingsSearch.swift:17-21`), and candidates are only titles plus keywords (`:23-30`). Working the rule against `SettingsItem+Catalog.swift`: “settings.json” splits into `settings` + `json`; the Settings file item offers `settings`, `file`, `configuration`, `location`, `path`, `finder`, so the exact filename the user is hunting returns the “No Results” overlay (`SearchResultsList.swift:13-18`). “brew” fails against the keyword “Homebrew” because the match is a prefix, not a substring. “models” fails to find the _Model_ setting, since `model`.hasPrefix(`models`) is false, though it does find the pane. Separately, result rows show only a title and its pane (`SearchResultsList.swift:22-41`), so “API key” — a match the test suite pins (`SettingsSearchTests.swift:47-53`) — leads to the Providers & Accounts scaffold with its disabled Add Provider… (`03-providers-light.png`, which I opened) and nothing in the result warns that this pane is not connected.
- **Principle/source:** Apple HIG, _Search fields_ — “Apps such as Settings take advantage of search to quickly filter the sidebar and expose sections that may be multiple levels deep,” plus “Consider showing suggested search terms” (first-party, https://developer.apple.com/design/human-interface-guidelines/search-fields, accessed 2026-11-07). Nielsen heuristic #6, recognition rather than recall (URL above, accessed 2026-11-07). Krug, _Don’t Make Me Think_: a failed search is read as “the feature isn’t there”, not “my wording was wrong”. Book.
- **User impact:** Task 5, and task 3 through it. A developer typing the filename they already know gets “No Results” for a row that exists; a user typing a credential term is routed to a pane that cannot do anything, with the “not connected” fact — a hard rule in the brief — appearing only after the trip. Demonstrated from code and tests; the user’s interpretation of a zero-result is plausible.
- **Recommendation:** **[polish]** Add Edit ▸ Find (⌘F) focusing the sidebar field — a keyboard route to an existing control, under the brief’s keyboard commitment — and carry the pane’s unconnected state into the result row with the same wording the panes use (“Not connected”), so search cannot promise more than the destination delivers. **[proposal]** Loosen matching for the last query word to a substring, or add the filename and `brew` to the relevant keywords. Tradeoff: substring matching makes short queries noisier and would need the sidebar-order ranking in `SettingsSearchTests.swift:60-73` re-checked.
- **Severity / confidence:** medium / medium-high (rule and catalog read from source and tests; no capture of the results list, and System Settings’ own matching behavior was not tested here).
- **Validation needed:** Type “settings.json”, “brew”, “models”, “api key” against the running build and record results; verify SwiftUI does not already install ⌘F for `.searchable(placement: .sidebar)` on macOS 27 before adding a command that would duplicate it.

## Worth keeping

- **Per-action Homebrew confirmations that name the side effects, not just the verb** (`HomebrewAction+Presentation.swift:22-33`): tap-wide trust is described as tap-wide, cleanup is described as disabled, and reinstall warns about running sessions. This is the strongest interaction writing in the app and the brief rightly fixes it.
- **Optimistic selection with an honest rollback** (`ModelSettings.swift:194-215`, `PendingModelSettings.swift`): the picker answers immediately, queued changes stay ordered, a failed save reverts to the confirmed value and reports its cause in an alert. That is the right model for a settings window with no Save button.
- **The `provider/id` carried in Available models** (`ModelRows.swift:78-101`; captures 11 and 13, which I inspected): the picker shows short names, and the list below lets the user recognize which `qwen/qwen3-coder-30b` the footer means. Keep that pairing if the picker is ever restyled.
- **Honest read-only status labels instead of fake toggles in Tools & Integrations** (`04-tools-light.png`, which I inspected): a fixed policy presented as fixed, with Included and Excluded as separate groups. Task 4 is the one job in the brief with no interaction finding.

## Lens score

**6/10.** Rubric: discoverability of the next action, feedback during and after each action, fit between control and mental model, error prevention, and recovery from error — weighted by the brief's five tasks. The app scores well on two of these: feedback during _saving_ is modelled carefully and reverts honestly, and error _prevention_ around Homebrew is better than most apps manage. It loses points on recovery and on the proportionality of its signals: three of the five tasks end in a state where the offered control repeats a failure (INT-3), omits itself (INT-4), or is absent for the longest operation (INT-1), and the one attention signal in the window is pointed at the benign case (INT-2).

What I could not assess: every loading, saving, Homebrew-action, confirmation-dialog and search state is absent from the captures, so those findings rest on source reading and are marked as such; no behavior was executed, because the review is read-only on the user's Mac. Keyboard-only traversal, real VoiceOver output, Increase Contrast, Reduce Motion and the active-window appearance were out of reach here, so claims about focus order and announcement are untested. No user research exists, so every mental-model claim in this report is a hypothesis about one developer-user.

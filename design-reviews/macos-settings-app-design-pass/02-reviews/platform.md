# Platform and system fit review

Reviewer: platform and system fit. Brief version 1. Evidence: index of 2026-11-07.

## Findings

### PLA-1 Messages that predict a failure are drawn as neutral helper text

- **Observation:** I opened `01-evidence/before/13-scratch-models-set-light.png` and `14-scratch-models-saved-unavailable-light.png`. The neutral footer in 13 ("Pico uses this model and reasoning level for new sessions…") and the warning footer in 14 ("The saved model or reasoning level is unavailable. New sessions will fail to start until you choose an available model and level.") are typographically identical: same size, same secondary gray, same position, no symbol. `16-scratch-models-invalid-file-light.png` is the same — a raw parser message (`$: not JSON: JSON Parse error: Unexpected EOF`) leads the footer with no status marker. Code: `app/Panes/ModelDefaultsFooter.swift` returns a bare `Text` for all six cases, including the two that say new sessions will fail. The app _does_ have a caution convention — `Label(…, systemImage: "exclamationmark.triangle")` in `app/Panes/ModelsPane.swift:16-19`, `app/Runtime/RuntimeSection.swift:21`, `app/Panes/SettingsFileRow.swift:19` — but it is confined to the inside of a group box, and in `SettingsFileRow.swift:20` the whole label (triangle included) is forced to `.secondary`, which is why the triangle in `01-general-light.png` next to "Couldn't load" renders gray rather than a caution color.
- **Principle/source:** Apple HIG, _Alerts_ → macOS: "Use a caution symbol sparingly. Using a caution symbol like `exclamationmark.triangle` too frequently in your alerts diminishes its significance. Use the symbol only when extra attention is really needed" — https://developer.apple.com/design/human-interface-guidelines/alerts (accessed 2026-11-07; first-party platform guideline). The corollary the app is missing is that the symbol _is_ the macOS marker for "extra attention is really needed," and the states in 14/16 are exactly that class. Secondary source: the app's own established warning component (code, cited above) — design-system consistency.
- **User impact:** Core job 2 (choose the default model). In state 14 the pane is fully populated and looks healthy — a model name sits in the pop-up, the catalog lists six models — and the single sentence saying new sessions will not start is styled exactly like the explanation shown when everything is fine. Demonstrated: the two captures are indistinguishable at a glance in the footer region. Plausible: a user scanning the pane concludes the default is set and leaves.
- **Recommendation:** **[polish]** Give the footer a severity treatment instead of one flat style: render the "will fail to start", "no usable credentials" and invalid-file cases as a caution `Label` (triangle + text) in the system's caution color, keep the informational cases plain, and stop forcing `.secondary` onto the triangle in `SettingsFileRow`. Wording stays as is — this changes only how severity is encoded. Tradeoff: three caution markers now exist on a bad General pane (settings file, runtime action, model footer); keep the symbol out of the purely informational footers so it does not become decoration, per the HIG line above.
- **Severity / confidence:** high / high (both captures inspected; code read).
- **Validation needed:** Re-capture 13, 14 and 16 side by side after the change in both appearances and with Increase Contrast on, and confirm the caution color is a system color so it adapts; confirm VoiceOver still reads the footer as one sentence and not "warning" twice.

### PLA-2 The pane header card repeats the window title and pushes General past the default window height

- **Observation:** Every pane opens with a rounded card holding a 32 pt colored tile, the pane title, and the pane summary (`app/Panes/PaneHeader.swift`; visible in all six light captures). The same title is already in the toolbar, in the macOS window title (`01-general-light.ax.txt:1` → `AXWindow title="General"`), and in the selected sidebar row. On `03-providers-light.png` the stack is worse: "Providers & Accounts" (card) → "Providers" (section header) → "Providers" (row label) → "Not connected", because `app/Panes/ProvidersPane.swift:10,12` uses `SettingsItem.providerList.displayTitle` for both the header and the row. Measured off `01-general-light.png` (715 × 849 pt window, 2 px/pt): the toolbar separator sits at ≈52 pt, the card spans ≈76–122 pt, and the first section header "Runtime" starts at ≈158 pt — the header block costs ≈105 pt before any setting appears. General's content ends at ≈754 pt. Against the app's default window height of 680 pt (`app/PicoApp.swift:21`), minus toolbar (~52 pt) and the scaffold bar (~39 pt), the visible content area is ≈589 pt while General needs ≈720 pt, so roughly 130 pt — most of the Versions group and its footer — is below the fold at the size the window actually opens at. (The ≈130 pt figure is arithmetic from the capture plus the code-declared default height, not an observed 680 pt capture; the index notes no capture was taken at 680 pt.)
- **Principle/source:** Apple HIG, _Settings_ → macOS: "Update the window's title to reflect the currently visible pane" — the pane's identity is specified to live in the title bar, which this app already does correctly: https://developer.apple.com/design/human-interface-guidelines/settings (accessed 2026-11-07; first-party). Apple HIG, _Boxes_: "Prefer keeping a box relatively small in comparison with its containing view… it can crowd other content" and "Provide a succinct introductory title **if it helps clarify** the box's contents" — https://developer.apple.com/design/human-interface-guidelines/boxes (accessed 2026-11-07; first-party).
- **User impact:** Core jobs 1 and 3 (confirm Pico runs; find the settings file). Demonstrated: on General the three Versions rows and "Installed versions are not read here." fall outside the default window. Plausible: the brief's "primary job readable at a glance" is spent on a title the user just clicked.
- **Recommendation:** **[polish]** Keep the one-line summary, drop the duplicated title and the box around it: render the summary as a plain lead-in paragraph above the first section (optionally keeping a small tile), and keep the `.accessibilityAddTraits(.isHeader)` so the VoiceOver landmark survives. Separately, retitle the Providers section header or the row so the same word does not appear twice in one group. Tradeoff: the colored tile is the only in-pane confirmation of which pane you are in for a user who navigated by `pico://` link; the toolbar title and sidebar selection already carry that, and the reveal outline (capture 07) confirms the target. If Mark wants the tile kept, shrinking the block (16 pt tile, no box, tighter padding) recovers most of the 105 pt.
- **Severity / confidence:** high / medium (card geometry measured from a capture; the overflow is computed against the code-declared default height rather than observed).
- **Validation needed:** Launch at the default 680 pt and capture General before/after; confirm the last Versions footer is visible without scrolling and that the pane still reads correctly at the 520 pt minimum height (`SettingsWindowView.swift:32`).

### PLA-3 Actions escape the grouped box into section footers, in three different ways across panes

- **Observation:** I compared four captures. `01-general-light.png`: "Check Runtime" and "Check for Updates" sit **inside** the Runtime box (`app/Runtime/RuntimeSection.swift:27-31`). `02-models-light.png`: "Try Again" sits **inside** the Defaults box. `03-providers-light.png`: "Add Provider…" sits **outside** the box, floated right in the footer paragraph (`app/Panes/ProvidersPane.swift:14-19`). `16-scratch-models-invalid-file-light.png`: "Show in Finder…" sits **outside** the box, left-aligned under two lines of footer text (`app/Panes/ModelDefaultsFooter.swift:12-17`). So the same app places push buttons in three positions relative to the group container, and the two footer placements also disagree on alignment.
- **Principle/source:** Apple HIG, _Boxes_: "A box creates a visually distinct group of logically related information and components" — the box is what signals membership; a control outside it reads as unrelated to the group it acts on: https://developer.apple.com/design/human-interface-guidelines/boxes (accessed 2026-11-07; first-party). The System Settings idiom the brief names as authority keeps action buttons inside the grouped container and reserves the text below it for explanation; the app follows that in General and Models-failed and breaks it in Providers and Models-invalid (code-derived + capture comparison).
- **User impact:** Core job 3 (find the settings file) in its worst state: when `settings.json` is unparseable, the one button that gets the user to the file is the element most easily read as part of a paragraph of gray prose rather than as the pane's recovery action (capture 16). Plausible, not demonstrated — no usability data.
- **Recommendation:** **[polish]** Move "Show in Finder…" into the Defaults group as the trailing control of a caution row (matching the "Couldn't load model settings / Try Again" row already built in `ModelsPane.swift:14-27`), and move "Add Provider…" into the Providers group, leaving only explanatory prose in the footers. Capability is unchanged; "Add Provider…" stays disabled. Tradeoff: the Providers group becomes a one-row box with a button, which looks sparse — acceptable, and it is what the pane will need once providers are connected.
- **Severity / confidence:** medium / high (four captures inspected; placements confirmed in source).
- **Validation needed:** Re-capture 03 and 16; confirm keyboard tab order still reaches the buttons after the rows, and that the invalid-file message still fits without widening the window.

### PLA-4 Sidebar tiles are a hard-coded 20 pt and mix solid with outline glyphs

- **Observation:** `app/Navigation/DestinationList.swift:29` and `app/Search/SearchResultsList.swift:27` both call `AppIconTile(destination:size: 20)` — a fixed size inside a `Label`. `app/Shared/AppIconTile.swift:12-18` builds the glyph with `.resizable().scaledToFit().fontWeight(.semibold)` inside a fixed frame with 20 % padding. Two consequences are visible in `01-general-light.png`, which I inspected: the Diagnostics stethoscope and the Sesh display glyph are thin outline line-art while General, Providers, Models and Tools are solid, so the six tiles do not share an optical weight; and because every glyph is scaled to fill the same inset box, stroke thickness tracks each symbol's aspect ratio rather than a chosen weight.
- **Principle/source:** SwiftUI `EnvironmentValues.sidebarRowSize`: "On macOS, reflects the value of the 'Sidebar icon size' in System Settings' Appearance settings… SwiftUI views like `Label` automatically adapt to the sidebar row size" — https://developer.apple.com/documentation/swiftui/environmentvalues/sidebarrowsize (accessed 2026-11-07; first-party developer documentation). Apple HIG, _SF Symbols_ → Weights and scales: symbols ship in nine weights matched to San Francisco and three scales, and "Specifying a scale lets you adjust a symbol's emphasis compared to adjacent text" — the sanctioned way to size a symbol is weight/scale, not arbitrary resizing; Design variants: "The solid areas in a fill variant tend to give a symbol more visual emphasis" — https://developer.apple.com/design/human-interface-guidelines/sf-symbols (accessed 2026-11-07; first-party). Apple HIG, _Sidebars_ → macOS: "A sidebar's row height, text, and glyph size depend on its overall size… people can also change it by selecting a different sidebar icon size in General settings" (page updated 2026-06-08) — https://developer.apple.com/design/human-interface-guidelines/sidebars (accessed 2026-11-07; first-party).
- **User impact:** Core job 5 (find any pane or setting). For a user who has set Sidebar icon size to Large, the `Label` text and row metrics grow while the tile stays 20 pt, so the sidebar and the search results list — the two places the tile appears — go visibly off-metric. This is [INFERENCE] from the documented behavior of `Label` and the hard-coded frame; the evidence index records no capture at a non-default sidebar icon size. The glyph-weight mismatch is demonstrated in capture 01.
- **Recommendation:** **[polish]** Read `@Environment(\.sidebarRowSize)` in `DestinationList`/`SearchResultsList` and map it to tile sizes (roughly 16 / 20 / 24 pt), leaving the 32 pt header tile independent; and configure the glyph with a font size and symbol weight/scale rather than `.resizable().scaledToFit()`, so all six tiles share an optical weight. For Sesh and Diagnostics, prefer symbols whose solid form matches the other four rather than thickening outline art. Tradeoff: per-symbol inset tuning is still needed for wide glyphs — the existing 20 % padding comment in `AppIconTile.swift:10-11` documents why it was done this way; keep that intent, just drive it from the symbol's own metrics.
- **Severity / confidence:** medium / medium (fixed size and the mixed glyph set are certain; the Large-sidebar outcome is untested).
- **Validation needed:** Set System Settings › Appearance › Sidebar icon size to Small, Medium and Large and capture the sidebar and a search result list at each; compare tile-to-text alignment against System Settings' own sidebar at the same setting.

### PLA-5 "Not connected" rows render at three different strengths inside a single row

- **Observation:** I inspected `05-sesh-light.png`. In the "Sesh custom agent" row the label is full-strength primary text, the value "Not connected" is secondary gray, and the "Register" button is dimmed — three different renderings of one state in one row, confirmed disabled only for the button in `05-sesh-light.ax.txt:56` (`AXButton description="Register" disabled`; the surrounding `AXStaticText` elements carry no disabled state). The same pattern holds across `03-providers-light.png`, `06-diagnostics-light.png` and the Versions group of `01-general-light.png`: inert rows look exactly like the live, connected rows above them, and nothing but the word "Not connected" distinguishes them. The window-level bar "Some settings aren't connected yet" (`app/Navigation/ScaffoldNotice.swift`) appears on five of six panes including General and Tools, where most content _is_ connected.
- **Principle/source:** Apple HIG, _Settings_ → macOS: "Dim a settings window's minimize and maximize buttons" — the HIG's stated mechanism for "present but not usable" on macOS is dimming, which this app applies correctly to buttons and not to the rows carrying the same meaning: https://developer.apple.com/design/human-interface-guidelines/settings (accessed 2026-11-07; first-party). Apple HIG, _Boxes_: a box groups "logically related information and components" — a live row and an inert row sharing one box with identical weight work against that grouping (same URL as PLA-3, accessed 2026-11-07). Internal consistency with the app's own disabled-button treatment (code, `ProvidersPane.swift:18`, AX outline above) is the second source.
- **User impact:** Core jobs 1 and 4 (confirm the runtime; understand the tool policy). On General, "Installation / Installed" and "Pico app / Not connected" are drawn identically, so the honest scaffolding rule is carried entirely by reading the value text. Plausible, not demonstrated: a user skims the Versions group and takes "Not connected" to mean a connection failure rather than "this app never reads this." The bottom bar is a non–System Settings element that restates, at window level, what each row already says, and on General and Tools it attaches a global caveat to mostly-connected panes.
- **Recommendation:** **[polish]** Render inert rows with the system's unavailable appearance — dim the label to match the value so the whole row reads as one state — while keeping the words "Not connected" so the state survives dimming and still reaches VoiceOver (the AX value is already correct). Then reconsider the bottom bar: once rows are honestly dimmed, it can shrink to the panes that are wholly scaffold (Providers, Sesh, Diagnostics) rather than appearing on General and Tools. Tradeoff and gate: dimming lowers contrast, and the brief commits to Increase Contrast support — this change must be measured against that commitment before it ships, and if secondary-on-grouped-background fails, keep the label at full strength and instead unify the row's value column with a single consistent unavailable treatment. No capability or wording changes either way.
- **Severity / confidence:** medium / medium (rendering observed in four captures and the AX outline; the contrast consequence of the fix is untested and may constrain it).
- **Validation needed:** Prototype one dimmed scaffold group, measure label-to-background contrast in Light, Dark and Increase Contrast, and run VoiceOver over Providers to confirm the row still announces label plus "Not connected" exactly once.

## Worth keeping

- **The window title tracks the visible pane.** `01-general-light.ax.txt:1` and `05-sesh-light.ax.txt:1` show `AXWindow title="General"` / `"Sesh"`, which is precisely what the HIG _Settings_ macOS section asks of a multi-pane settings window. Do not lose this if the header card (PLA-2) changes.
- **Grouped `Form` with explanatory section footers, and inline recovery inside the box.** The Runtime group in `01-general-light.png` — three status rows, two action buttons, one footer sentence — is the System Settings idiom done correctly, and the Homebrew per-action `confirmationDialog` (`RuntimeSection.swift:53-62`) is the right modality for a destructive-ish system action. PLA-3 asks the other panes to match _this_, not the reverse.
- **Native navigation instead of an invented one.** Back/forward in the toolbar's `.navigation` placement with ⌘[ / ⌘] menu commands (`SettingsCommands.swift:15-27`), ⌘, for Settings, the sidebar search field via `.searchable(placement: .sidebar)`, and the deliberately fixed sidebar with `sidebarToggle` removed — the last is a departure from the HIG _Sidebars_ "consider letting people hide the sidebar" advice, but it is the System Settings behavior the brief names as authority, and it stays understandable because there is nothing to reveal.
- **The reveal outline uses shape plus the user's accent color.** `SettingsReveal.swift:32-37` strokes a 2 pt continuous-corner rectangle in `Color.accentColor` with a 12 % fill; capture `07-reveal-tools-wait-light.png` shows it reading as a system focus treatment, not a custom highlight, and it respects the user's accent choice rather than a hard-coded blue.

## Lens score

**8/10.** Rubric: (a) correct first-party container and navigation for the task — split view, fixed sidebar, grouped forms, pane-tracking window title, system pop-up buttons, confirmation dialogs, accent-driven reveal: strong; (b) component consistency within the app — weakened by three button placements relative to the group box (PLA-3) and three text strengths for one state (PLA-5); (c) status and severity expressed the platform way — the main deduction, since the app owns a caution convention and does not apply it where failure is being predicted (PLA-1); (d) respect for system-level user settings — sidebar icon size is ignored and symbol weight is overridden (PLA-4); (e) intentional departures remaining understandable — the fixed 715 pt width, the removed sidebar toggle, the fixed-color tiles (a real tension with the _Sidebars_ guidance updated 2026-06-08, which asks sidebar icons to follow the user's accent color and reserves fixed colors for sparing, meaning-bearing use) and the bottom scaffold bar all read as deliberate System Settings or honesty-rule choices, and I do not recommend reversing them; the pane header card is the one departure that costs more than it returns.

Could not assess: active-window appearance (every capture is inactive, so accent-colored sidebar selection and toolbar emphasis are unseen); Increase Contrast and non-default sidebar icon sizes; the search results list and "No Results"; all loading, saving and Homebrew-result states; expanded Error Details; keyboard-only traversal and VoiceOver speech. I ran no build, no app launch and no interaction — every visual claim comes from the named PNG, every behavioral claim from the named source file or AX outline.

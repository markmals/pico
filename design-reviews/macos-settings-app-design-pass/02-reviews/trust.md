# Choices and trust review

Reviewer: Choices and trust. Brief version 1. Evidence: index of 2026-11-07.

## Findings

### TRU-1 A credential denial is presented as an anonymous “Couldn’t load” with a retry that cannot succeed

- **Observation:** I opened `01-general-light.png` (Real profile). Configuration › Settings file shows a caution triangle, “Couldn’t load”, a **Try Again** button, and a _collapsed_ “Error Details” triangle — and **no path at all**. `01-general-light.ax.txt:63-68` confirms accessibility clients get exactly the same four elements, with `AXDisclosureTriangle description="Error Details" value=false`. I opened `02-models-light.png` (same profile): both pickers read “Unavailable”, the row reads “Couldn’t load model settings” with Try Again and a collapsed Error Details, and Available models reads “Unavailable”. Per the evidence index (Profiles › Real) the underlying cause is a Keychain refusal (`KEYCHAIN_ACCESS_DENIED`, OSStatus −25293) on one selected credential. Code-derived: `app/Configuration/PicoCommand.swift:49-51` decodes `code` **and** `message` from `pico`'s error document, but the UI renders only `message` (`app/Shared/CommandErrorDetails.swift:7-20`); the `code` is consulted nowhere except the `"CONFLICT"` test in `app/Configuration/ModelSettings.swift:122`. The adapter additionally publishes `retryable`, and classes this code **non-retryable** (`adapter/cli/errors.test.ts:92-98`); `app/` never decodes that field (only a test fixture mentions it, `app/Configuration/PicoCommandTests.swift:85`). `app/Panes/SettingsFileRow.swift:18-22,32-34,39-42` confirms the path and the Copy Path command are both withheld in `.failed`.
- **Principle/source:** Apple HIG › Alerts, “Write a title that clearly and succinctly describes the situation… As much as possible, describe what happened, the context in which it happened, and why. Avoid writing a title that doesn’t convey useful information — like ‘Error’” (Apple developer documentation; https://developer.apple.com/design/human-interface-guidelines/alerts, accessed 2026-11-07). Nielsen heuristic 9, “Help Users Recognize, Diagnose, and Recover from Errors”: messages should “precisely indicate the problem, and constructively suggest a solution”; heuristic 1 warns that unpredictable status erodes trust (research synthesis; https://www.nngroup.com/articles/ten-usability-heuristics/, accessed 2026-11-07). The brief’s own fixed constraint — “failures reach the user with their cause (Error Details)” — is met only in the letter.
- **User impact:** Hits two of the brief’s five core jobs at once: “find the settings file” (job 3) and “choose the default model” (job 2). Demonstrated from the captures: the user sees a failure headline that cannot distinguish _macOS refused this binary access to a credential_ from _your settings file is gone/corrupt_, and the single visible affordance is a retry. Plausible, not demonstrated: the user presses Try Again repeatedly, then goes looking for a damaged settings file that is fine. The index calls this “a genuine state a user can reach after reinstalling or rebuilding `pico`” — i.e. immediately after the very Homebrew recovery this app exists to drive.
- **Recommendation:** **[polish]** Change only how existing information is presented: when a row enters its failure state, expand the Error Details disclosure by default (it is the only content there, and `ViewThatFits` already caps it at 120 pt so it cannot displace the recovery controls), and lead the detail line with the sentence `pico` returned rather than hiding it behind a triangle. **[proposal]** Reading the `code`/`retryable` fields the adapter already sends — to replace “Try Again” with an action that can work, to name the credential involved, or to keep the last-known settings path visible beside the failure — changes what the user can find out and needs Mark. Tradeoff for the polish: an expanded disclosure adds vertical noise in a 680 pt default window and makes a raw CLI sentence the first thing the user reads; that is still better than a headline carrying no cause.
- **Severity / confidence:** high / high (capture + AX outline + source; I did not run the app).
- **Validation needed:** Reproduce the Keychain denial, read the exact `message` string `pico settings get` prints, and check it names Keychain and a fix. Then watch one person in this state and record whether they press Try Again more than once and whether they open Error Details unprompted.

### TRU-2 A confirmed Homebrew action cannot be stopped, and the ordinary way to quit kills it mid-flight

- **Observation:** Code-derived; the index lists Homebrew confirmations and progress rows under “Not captured”. In `app/Runtime/RuntimeSection.swift:33-45` a Cancel button is offered for `.checking` and `.checkingUpdates`, and `EmptyView()` for `.running` — the cheap, side-effect-free checks are interruptible; the package operation is not. Everything else in the section is disabled while busy (`:32`). `perform` runs `brew install|reinstall|upgrade` with a 1800-second timeout (`app/Runtime/PicoRuntimeClient.swift:158-162`, `actionTimeout = 1800` at `:75`), and the only feedback is an indeterminate spinner plus “Installing Pico…” (`RuntimeActivityStatus.swift:8-9,19`, `HomebrewAction+Presentation.swift:13-20`). Meanwhile closing the window quits the app (`RuntimeTerminationDelegate.swift:21-23`; guide `guides/refining-the-mac-app-ui.md:31`), and termination calls `runtime.cancelAndWait()` (`RuntimeTerminationDelegate.swift:10-19`) → `RuntimeReadiness.cancel()` → `running.cancel()` (`RuntimeReadiness.swift:60-74`), which stops the whole process group Homebrew leads (`HomebrewCommand.swift:67-69`). Nothing in the confirmation text or the progress row says so. The app already models the wreckage that interrupting a reinstall produces: `.unlinked` → “Not linked … Reinstall to restore its command link” (`RuntimeUpdatesRow.swift:34-41`).
- **Principle/source:** Apple HIG › Progress indicators: “**When it’s feasible, let people halt processing.** If people can interrupt a process without causing negative side effects, include a Cancel button. If interrupting the process might cause negative side effects … provide a Pause button in addition”, and “**Let people know when halting a process has a negative consequence.**” Also “When possible, use a determinate progress indicator… [it] can help people decide whether to do something else while waiting” (Apple developer documentation; https://developer.apple.com/design/human-interface-guidelines/progress-indicators, accessed 2026-11-07). Nielsen heuristic 3, User Control and Freedom: people need “a clearly marked ‘emergency exit’” (same NN/g URL, accessed 2026-11-07). Norman, _The Design of Everyday Things_, rev. ed. (MIT Press, 2013), on designing for error: make actions reversible and make the cost of an exit visible (book; https://mitpress.mit.edu/9780262525671/the-design-of-everyday-things/).
- **User impact:** Core job 1 — recover a broken install. The window gives no exit for up to 30 minutes, so the exit people actually take is the red button, which is also the quit command and silently aborts `brew`. Demonstrated: the absence of a Cancel and the cancel-on-quit path are both plain in the source. Plausible, not demonstrated: that an aborted `reinstall` lands the user in the “Not linked” state — i.e. the app’s one uninterruptible action can manufacture the condition it exists to repair.
- **Recommendation:** **[polish]** Add the consequence to the text already shown: say in each confirmation that the action runs until it finishes and that closing the window stops it, and replace the bare spinner label with the command being run so the wait is legible. **[proposal]** Offering a Cancel (or a confirm-before-quit prompt) during `.running` changes what the user can do — raise it as a deferred decision; it is the honest fix, because the current asymmetry hands the safe operations an exit and withholds one from the risky operation. Tradeoff: a real Cancel needs a defined stop point for `brew`, and an unclean stop is itself damaging — which is exactly why the warning text is the minimum.
- **Severity / confidence:** high / medium (source is unambiguous; the damage from an aborted reinstall is reasoned, not tested).
- **Validation needed:** Start a reinstall against a scratch Homebrew prefix, close the window mid-run, and record the resulting `brew list`/link state; confirm whether the next launch reports “Not linked”.

### TRU-3 The sidebar’s one attention badge marks the working state and stays silent on the failing one

- **Observation:** I opened `11-scratch-models-not-set-light.png`: Models carries a prominent “1” badge in the sidebar while the pane’s footer reads “Until you choose a model, Pico uses lm-studio/qwen/qwen3-coder-30b for new sessions without a model override from Sesh” — i.e. sessions work. I opened `14-scratch-models-saved-unavailable-light.png`: **no badge**, while the footer reads “The saved model or reasoning level is unavailable. New sessions will fail to start until you choose an available model and level.” Code-derived: the badge is driven solely by `destination == .models && defaultModel == nil` (`app/Navigation/DestinationList.swift:32-39`), with accessibility value “Default model not set”. Secondary, same capture: in the not-set state Reasoning level reads “Not Set” and is dimmed, and the footer names only the fallback _model_ — although the app holds `effective.defaultThinking` in the same payload (`app/Configuration/PicoModelSettings.swift:42-46`; `PicoSettingsReadTests.swift:11` shows `"effective":{…"defaultThinking":"high"…}` arriving), and `ModelDefaultsFooter.swift:34-37` interpolates only `effective.defaultModel`. The named fallback is also printed as a raw slug while the list two rows below shows friendly names.
- **Principle/source:** Apple HIG › Alerts, macOS: “**Use a caution symbol sparingly.** Using a caution symbol … too frequently in your alerts diminishes its significance” — the dilution argument applies identically to an attention badge (Apple developer documentation; https://developer.apple.com/design/human-interface-guidelines/alerts, accessed 2026-11-07). Nielsen heuristic 1, Visibility of System Status: “no action with consequences to users should be taken without informing them” (https://www.nngroup.com/articles/ten-usability-heuristics/, accessed 2026-11-07). [INFERENCE] macOS System Settings reserves this badge style for conditions that need the user’s action; I did not capture System Settings to prove the convention.
- **User impact:** Core job 2. The glanceable signal is inverted against consequence: the benign, fully-disclosed state is flagged, and the state in which _every new session will fail_ is not. Plausible, not demonstrated: a user who has learned the badge means “needs attention” reads its absence in capture 14 as “nothing to do here”. The reasoning-level gap is a smaller, demonstrated disclosure hole — what level your sessions actually run at is knowable to the app and not shown.
- **Recommendation:** **[polish]** Make the badge track consequence rather than emptiness: no badge while a disclosed fallback is carrying new sessions, badge when `item.defaultModel != nil && !effective.available` (the pane already states that consequence in words, so nothing new is revealed), and name the effective reasoning level alongside the fallback model in the footer using the readable label the pickers use. Tradeoff: dropping the not-set badge removes the nudge that got Mark to set an explicit default (Beads `pico-bfk.10`), and an implicit default can change between `pico` versions — so if the nudge is worth keeping, it should at minimum not be _louder_ than the failure state. The label choice is presentation; if Mark considers the badge’s trigger a behavioral contract, treat the retarget as a **[proposal]**.
- **Severity / confidence:** medium / high for the observation, medium for the remedy (no evidence on how Mark reads the badge).
- **Validation needed:** Put both states in front of a user cold and ask which pane needs their attention; confirm `pico settings get` always supplies `effective.defaultThinking` when it supplies `effective.defaultModel`.

### TRU-4 “Providers — Not connected” reads as a verdict on the user’s accounts, and in the capture it is false

- **Observation:** I opened `03-providers-light.png` (**Real** profile). The pane shows a group headed “Providers” with one row, `Providers — Not connected`, a disabled **Add Provider…**, and the footer “Supported providers come from the engine; none are listed here.” `03-providers-light.ax.txt:44-48` shows accessibility clients receive the same: label “Providers”, value “Not connected”. In that same Real profile the user _does_ have a selected provider credential — the Keychain refusal reported in the index is a refusal to read _the selected Anthropic credential_. So on the user’s own machine, a pane titled “Providers & Accounts” states that their providers are not connected. Source: `app/Panes/ProvidersPane.swift:9-20`. Contrast `05-sesh-light.png`, which I also opened: every Sesh group footer attributes the state to the app — “The helper’s location is not resolved while settings stay unconnected”, “Nothing is read from Sesh, and no registration is inspected”, “Guided setup through Sesh is not available from this scaffold.” Providers is the outlier; its footer asserts a fact about the world instead.
- **Principle/source:** Project rule (`AGENTS.md:223`): “A control must not report a value it does not have” — and `proposals/0005-mac-app-ui-workspace.md:86` sets the string as an example (“neutral placeholders **such as** ‘Not connected’”), not as fixed wording, which keeps the footer squarely inside the brief’s permitted “wording that is not itself a requirement”. GOV.UK design principle 4, “Do the hard work to make it simple… especially when the underlying systems are complex”, and principle 9, “Be consistent, not uniform” — the Sesh pane already holds the better pattern (https://www.gov.uk/guidance/government-design-principles, updated 2 April 2025, accessed 2026-11-07). Nielsen heuristic 2, Match Between the System and the Real World: the phrase has to mean what the user will read into it (https://www.nngroup.com/articles/ten-usability-heuristics/, accessed 2026-11-07).
- **User impact:** No core job depends on this pane today, which is why it ranks fourth — but it is the second item in the sidebar and it is the first thing a user checks when Models says “Unavailable”. Demonstrated: the capture states “Not connected” for a user who has a connected, selected credential. Plausible: the user concludes their sign-in was lost and goes hunting for a credential problem that does not exist — the exact confusion the user guide pre-empts in prose the app never shows (`guides/refining-the-mac-app-ui.md:133`, “‘Not connected’ … is not a diagnosis of your installation”).
- **Recommendation:** **[polish]** Rewrite the footer in the Sesh pane’s voice so the sentence is about the app, not the account — e.g. state plainly that provider accounts are not read here yet and that connected credentials are managed with `pico`'s commands. Keep the row value and the disabled button exactly as they are, so the hard rule and its accessibility commitment are untouched. Tradeoff: a longer footer on an otherwise nearly empty pane, and it names the CLI in a GUI; the alternative — changing the row value itself — touches a string quoted in `AGENTS.md` and should go to Mark.
- **Severity / confidence:** medium / high (two captures, one AX outline, source).
- **Validation needed:** Confirm with Mark that the Real-profile capture was taken with a selected Anthropic credential in place (the index’s Keychain note implies it). Ask one user what “Providers — Not connected” tells them about their own account.

### TRU-5 The tap-wide trust grant states its breadth but not its lifetime, its revocation, or that a narrower grant exists

- **Observation:** Code-derived (the index lists Homebrew confirmations as not captured). The dialog reads “Trust markmals/tap?” / “This lets Homebrew run formula code from markmals/tap on this Mac. Trust applies to the entire tap, not just Pico. Installing Pico still requires a separate confirmation.” (`app/Runtime/HomebrewAction+Presentation.swift:9,30-32`) — an unusually frank disclosure of breadth, and the separation from install is correct. What is missing: the grant is persistent, covers every formula the tap ever adds, survives uninstalling Pico, and cannot be withdrawn anywhere in this app — `RuntimeReadiness.Recovery` has no revoke case (`RuntimeReadiness.swift:336-342`) and the action set is install/reinstall/trust/upgrade only (`PicoRuntimeClient.swift:221-224`, where trust is `brew trust --tap markmals/tap`). A **narrower** grant is recognised as sufficient by Pico’s own check — `trusted.taps.contains(tap) || trusted.formulae.contains(formula)` (`PicoRuntimeClient.swift:294-295`) — but is never offered; `guides/refining-the-mac-app-ui.md:43` records this as deliberate (explicit tap-wide approval preferred over implicit formula trust). The grantee is the app’s own publisher, so the breadth benefits the publisher and the risk sits with the user. [INFERENCE] `RuntimeSection.swift:58` gives the confirm button no keyboard role, so SwiftUI’s standard placement applies and Return grants trust; I did not capture the dialog.
- **Principle/source:** Apple HIG › Privacy: “**Request access only to data that you actually need.** Asking for more … can make it hard for people to trust your app. Give people precise control … by making your permission requests as specific as possible” (Apple developer documentation; https://developer.apple.com/design/human-interface-guidelines/privacy, accessed 2026-11-07) — written for personal data, but it is Apple’s own statement of least privilege and transfers directly to a code-execution grant. Apple HIG › Alerts: “If you want to encourage people to read an alert and not just automatically press Return to dismiss it, avoid making any button the default button” (same alerts URL, accessed 2026-11-07).
- **User impact:** Core job 1, at its one security-consequential moment. Demonstrated from source: nothing in the app tells the user how long the grant lasts or how to take it back, and no narrower option is presented. Plausible: a user grants tap-wide trust believing it is scoped to this install, and a later formula added to the tap inherits it.
- **Recommendation:** **[polish]** Two sentences and one modifier: say that the grant stays until it is removed in Homebrew and is not undone by uninstalling Pico, and give Cancel the default keyboard action for `.trustTap` only (leave install/reinstall/update as they are — those are the user’s deliberately chosen intent, and HIG explicitly favours Return there). **[proposal]** Offering formula-only trust as the narrower choice changes what the user can do; given that `PicoRuntimeClient.swift:295` already accepts it, it is the recommendation with the best consent/benefit ratio and belongs in front of Mark. Tradeoff: an extra option in the dialog complicates a one-time decision, and tap-wide trust means the user is not re-prompted later — convenience that is worth having, but only as an informed choice rather than the only one.
- **Severity / confidence:** medium / medium (text and command are source-verified; the button role and the dialog’s rendering are not).
- **Validation needed:** Capture the trust dialog on a machine where Homebrew reports the tap untrusted, and confirm which button Return activates. Confirm what Homebrew 6 offers for withdrawing tap trust before naming any step — do not ship a revocation instruction that has not been run.

## Worth keeping

- **Preserving a saved default that has become unusable, and naming the consequence.** `14-scratch-models-saved-unavailable-light.png` (inspected) keeps `anthropic/claude-sonnet-5-5 (unavailable)` visible in the picker rather than silently substituting a working model, and says outright that new sessions will fail to start. That is the brief’s “never fall back silently” rule met in both directions — no quiet substitution, and the cost stated in the user’s terms.
- **Footers that refuse to overclaim.** “Command startup checks Pico, not provider sign-in or a model turn. Homebrew is refreshed only when you check for updates.” (`01-general-light.png`, inspected) tells the user precisely what a green “Passed” does and does not prove, and “Installed versions are not read here.” disclaims the Versions rows instead of letting them imply a reading. Scarce behaviour in settings UI; keep it.
- **The conflict message.** `ModelSettings.swift:182-191` refuses a stale save, discards pending changes, reloads, and explains all three — and escalates its own wording when the reload _also_ fails. Recovery stated as what happened to the user’s change, not as an error code.
- **The Sesh pane’s scaffold voice.** `05-sesh-light.png` (inspected) attributes every unconnected value to the app (“Nothing is read from Sesh, and no registration is inspected”), never to the user’s setup. This is the pattern TRU-4 asks Providers to adopt — it already exists in the product and should survive the revision.

## Lens score

**7/10.** Rubric factors: (a) are consequential defaults disclosed; (b) is consent for security-relevant actions specific, revocable and free of asymmetry; (c) do failures name their cause and a real recovery; (d) do users retain control and an exit; (e) is unconnected scaffolding honest about who it describes; (f) who benefits from the choice architecture.

Rationale: on (a) and (e) this app is better than most shipping settings UI — the implicit model fallback is named in place, an unusable saved default is preserved rather than replaced, and every pane carries a disclaimer rather than an implication. On (b) the tap-trust dialog volunteers the single most important fact (the grant is wider than Pico) and separates trust from install, which is why TRU-5 is a completion rather than a correction. The points come off (c), (d) and (f): the headline failure state suppresses a cause the app has already parsed and offers a retry the adapter classes non-retryable; the one irreversible, minutes-long operation is also the one with no exit, while its cheap siblings have one; and the sidebar’s single urgency signal is inverted against actual consequence. None of these are deceptive by intent — each is a disclosure that stops one layer short.

Could not assess: no Homebrew confirmation or progress state was captured, so TRU-2 and TRU-5 rest on source reading, and I did not verify which button Return activates in the confirmation dialog. The exact `pico` message a Keychain refusal produces was not read, so TRU-1’s claim is about the app’s presentation of that message, not its content. No save-failure alert, loading state, or empty-catalog state was captured. Active-window appearance was not captured; no VoiceOver, keyboard traversal or Increase Contrast was exercised in this run; no user research exists, so every claim about what Mark or another user would conclude is a hypothesis, labelled as such above. I ran no build and launched no app, per the review constraints.
